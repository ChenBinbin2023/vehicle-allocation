# 周度分车策略调整方案

> 版本：v0.2 · 设计与前端演示
> 日期：2026-09-30
> 范围：基于现有周度分车模块，设计 CUI 对话、GUI 分析看板、情景策略调整及结果解释。本文保留目标业务设计；已接入本地前端的完整故事见[演示脚本](./04_CUI与GUI完整故事脚本.md)。本地 Skill 读取 CSV 派生快照，尚未连接外部查询服务或生产资源求解。
> 配套：[数据分析 Dashboard](./02_数据分析Dashboard设计.md)、[港口受限策略与结果口径](./03_港口受限策略与结果解释.md)。

演示主线与输入台词：[CUI 与 GUI 完整故事脚本](./04_CUI与GUI完整故事脚本.md)；实现范围：[前端实施计划](./05_前端实施计划.md)。

## 1 业务目标与设计选择

用户先在 CUI 新建 session，说明车型和分货周期，系统在 GUI 创建一条周度分车任务。用户调用分析 skill 后，系统检查数据并解释供给、需求、库存和物流压力；用户进一步提出业务变化或修改参数，系统生成可比较的策略版本，试算到门店，说明每个经销商的要货满足率、物流费用以及没有分到车的原因。

推荐采用“**同一任务、共享数据版本、对话与工作台同步**”的方案。CUI 用来表达意图、追问和解释；GUI 用来浏览数据、检查参数差异、比较结果。两端读取同一分析产物和试算结果。

| 组织方式 | 优点 | 局限与选择 |
| --- | --- | --- |
| 同一任务内设置数据分析、策略调整、分车结果三个阶段 | 保留讨论上下文，可反复调整，容易比较前后结果 | 推荐；沿用原模块的参数、图谱和发布能力 |
| 做一个独立的静态分析报表 | 基线数据容易展示 | 参数与结果容易脱节，不能完成本次业务闭环 |
| 每提出一个情景就创建全新任务 | 情景之间隔离明确 | 同周资源容易重复占用，方案比较困难；改为任务内候选版本 |

本次成功标准是：用户能从一句业务诉求进入任务，从风险定位到参数变更，从试算结果追到证据；相同范围、版本和指标在两端一致。

## 2 与已有方案的关系

以[周度分车模块 v1.2](../01_周度分车/01_周度分车模块设计方案.md)及[计算节点与字段字典](../01_周度分车/02_计算节点与字段字典.md)为计算规则依据。既有[GUI 设计](../01_周度分车/03_GUI页面与交互设计.md)继续承接参数编辑、计算图谱、结果和发布，本方案补充前置分析与情景决策。

保留以下约束：

- 最小分车单位是经营周 × 销售网点 × 车型，数量为整数台；经营主体用于汇总和结算。配置、颜色、VIN 由后续执行模块处理。
- 每个车型先按 A1 拆直营池、授权池，再在池内处理有效订单和普通补库。不会自动跨车型替代，也不会自动跨渠道借车。
- 不恢复已经删除的保底功能。有效订单来自业务记录，不能把用户的“至少给几台”转换成虚构订单。
- A5 改变目标库存，A3 改变需求预测；政策倾斜不直接改写历史销量或实物库存。
- A9 车型搭配没有有效政策时关闭。启用后分别占用两个车型的渠道预算，不能以搭配绕过承接限制。
- B11 检查多车型共享路线、库容、额度和时间条件；通过前是候选量，通过后才称最终分车量。

旧故事材料仅引用其明确标注的 W1 演示数据。若其保底、配置粒度等叙述与 v1.2 不同，以 v1.2 为准。

## 3 用户完整工作路径

```mermaid
flowchart LR
    A[新建 session] --> B[CUI 描述车型与经营周]
    B --> C[GUI 创建周度分车任务]
    C --> D[调用分析 skill]
    D --> E[数据检查与供需库存物流分析]
    E --> F[CUI 结论与 GUI Dashboard]
    F --> G[业务情景或参数调整]
    G --> H[策略草稿与参数差异]
    H --> I[试算及共享资源校验]
    I --> J[结果对比与逐店解释]
    J --> G
    J --> K[选定版本并进入原发布流程]
```

### 3.1 新建 session 与任务

示例输入：“新建下周丰田分车任务，先看凯美瑞、卡罗拉和海拉克斯。”

系统解析任务类型、品牌、车型、经营周和范围。“下周”按业务时区 `Asia/Riyadh` 转为确切起止日，并在任务卡上显示完整七天。未知车型、模糊周界或用户只说“近期”时，在 CUI 补充必要字段，GUI 同时保留“待补充信息”的任务卡。

任务卡只显示一条周计划，内部展开车型子任务，避免一句“三个车型”产生三个互不关联的顶层任务。建议字段如下：

| 任务卡内容 | 展示规则 |
| --- | --- |
| 标题、经营周、业务时区 | 可读名称优先，不能只展示内部编号 |
| 品牌与车型 | 展示已选择车型数量，展开查看列表 |
| 网点范围 | 默认经营资格范围；演示网络共79店，不等于每车型都有79个合格网点 |
| 当前阶段 | 待分析、分析中、待补数据、待调整、试算中、待评审、已发布 |
| 当前方案与数据时间 | 标注演示/正式，能查看来源日期及版本 |
| 最新结论与下一操作 | 例如“历史销速较旧，可先查看品牌压力分析” |

创建请求带唯一请求标识；消息重试、网络重连不会重复建任务。同一 session 可以管理多项任务，后续修改必须有明确的当前任务；用户同时引用多个任务且无法判断时才需要定位任务。

### 3.2 调用数据检查与分析 skill

拟定义业务 skill `weekly-allocation-analysis`，界面名为“周度分车数据检查与分析”。这是待建设的能力名称，不是当前已安装的技能。

用户明确调用后，系统依次完成：

1. 读取任务范围，冻结输入快照，检查主键、关联、期间、单位、缺失及数据性质。
2. 查询供给、销量、库存、订单和物流资源；先判断哪些维度有充分数据，再计算。
3. 生成品牌、区域、渠道、门店及可用车型层面的分析指标。
4. 对库存偏低、供需结构错配、路线瓶颈和数据缺口给出证据和影响范围。
5. 同时输出 CUI 摘要和 GUI 所需指标、图表、明细及证据引用。

CUI 可折叠展示“已读取库存”“正在核对运力”等执行进度，以及必要的工具结果摘要，不展示内部推理过程。GUI 按检查完成的模块逐步加载；一项查询失败不会让其他已完成面板变成空白。

**CUI 摘要固定回答五件事**：当前可分析什么、供需矛盾在哪里、哪些库存和运输条件影响决策、哪些信息尚缺、下一步适合试算什么。默认控制在一个屏幕，明细通过点击打开 GUI。

以现有数据为例，摘要可写为：

> 已完成79家门店的品牌级检查。门店实物库存6,709台，其中自由库存5,232台，在途1,012台另列。仅吉达港的模拟道路运力为1,865台/周，低于双港口的3,226台；按历史需求计算，利雅得、吉达、达曼线路压力较大。当前销量窗口结束于7月，且缺逐店逐车型库存和在途到达日，可以先做品牌及路线压力分析；逐车型结果需接入明细，或显式建立演示假设后试算。

### 3.3 用户提出业务变化

示例：“霍尔木兹海峡未来会封闭，丰田供应下降，东部港口关闭，全部从吉达进入，帮我调整策略。”

系统将这句话保存为**用户提出的情景**，不作为已经发生的外部事实。先拆成供给量、入口、批次到达时间和道路运输条件四类影响，避免将一项变化重复扣减。

- 可以立即做：加载已有的仅吉达道路运力情景，展示与双港口的差异，分析当前门店库存和历史需求。
- 需要具体化：受影响车型、供应降幅、开始时间和持续周期，东部“港口入口”与“VPC存量发运”是否同时关闭，吉达承接量及释放时间。
- 信息尚缺时：可给条件式策略及明确标注的演示敏感性分析，不生成看似确定的正式分车结果。

页面把建议组织为可理解的策略卡，例如“紧缺车型减少非必要补库”“东部按到达时点保护有效订单”“高库存车型减少新增拿货”。展开后才显示所涉及的 A1/A3/A5 等参数。

### 3.4 修改参数并试算

自然语言和 GUI 表单共同编辑一个策略草稿。用户说“把这一轮凯美瑞目标降为3周，重新算一下”已经明确授权该范围的草稿修改和试算；不重复要求确认。用户只是问“应该怎么调”时先展示建议，不把建议直接当作已选策略。

应用建议前后始终能看到：参数原值、新值、范围、有效期、依据、受影响车型/渠道，以及可能牺牲的目标。GUI 修改可在 CUI 生成一句变更回执；CUI 修改会定位 GUI 中的对应字段。

一次试算冻结“输入快照＋情景＋参数＋算法＋共享资源版本”。此后继续修改草稿，不会改动正在运行的试算。新结果完成后用户可选择查看，旧结果保留比较；未重算期间显示“参数已修改，当前结果未更新”。

### 3.5 查看结果和作出选择

先给总览：分车量、渠道预算、未分配、要货满足率、有效订单及时满足率、预计国内道路费用、共享约束状态。再下钻到经营主体 → 门店 → 车型，解释每项变化。

CUI 总结“哪些问题改善、哪些代价增加、哪些缺口还在”。GUI 允许查看基线与候选的逐店差异，并追到原模块 B0–B12 证据。选定方案后进入原有校验与发布页；选择、试算、发布、发运是不同状态。

## 4 业务 skill 的输入输出与责任

| 能力 | 输入 | 可供两端共用的产物 |
| --- | --- | --- |
| 数据检查与分析 | 任务、查询范围、数据截止、输入快照 | 数据检查项、指标、图表数据、发现、证据、缺口清单 |
| 情景分析与建议 | 基线分析、用户情景、业务目标、当前有效规则 | 情景假设、车型策略组、参数草稿、影响范围和限制 |
| 分车试算 | 冻结后的数据、参数、情景及资源 | 原引擎节点产物、候选/最终结果、资源校验、费用估算 |
| 结果解释 | 指定运行、指定对比基线、主体/门店/车型 | 满足率分解、费用分摊、未满足原因及证据链 |

模型负责理解业务问题、选择分析路径、组织建议和解释。数量计算、规则校验、费用合计由确定性计算服务完成，解释读取同一份结果。模型不能用自由文本改写已经求出的分车量。

每条分析发现至少包含标题、结论、影响范围、指标值、期间、来源、数据性质、建议动作及受缺失数据影响的限制。图表和文字都引用指标标识；结论找不到输入或结果依据时，不展示为确定结论。

## 5 两端同步与状态设计

### 5.1 需要保存的对象

| 对象 | 作用 |
| --- | --- |
| Session | 对话、任务上下文及当前选中的任务 |
| AllocationTask | 经营周、车型范围、任务状态，关联原 S1 周计划 |
| AnalysisSnapshot | 输入版本、质量检查、分析指标和发现；可在尚未分车时存在 |
| ScenarioVersion | 供给/港口/时序/运输假设，不覆盖原始输入 |
| StrategyDraft 与 ParameterVersion | 可编辑建议与冻结规则，后者复用 S2 |
| AllocationRun | 一次试算及全部节点产物，复用原 run_id |
| Comparison | 明确的基线与候选版本、共同评估范围、分母及差异 |

输入来源日期与抓取时间分别记录。刷新数据会新建快照，不能把旧试算结果自动挂到新快照上。

### 5.2 事件及交互规则

拟采用任务事件驱动两端更新：任务创建、检查项完成、分析完成、草稿变更、运行启动、节点完成、运行完成、运行失败。事件携带任务、对象版本和递增序号；前端可重放、去重，晚到的旧运行不能覆盖新结果。

聊天消息关联其生成时的分析/运行版本。点击旧消息中的“查看数据”打开对应历史版本，并提示与当前版本的差异。页面仅筛选东部时，聊天摘要若讨论全国，必须显示全国范围；用户点击“针对当前筛选分析”才把筛选转为新问题的范围。

| 异常 | 页面及对话行为 |
| --- | --- |
| 缺少逐车型数据 | 品牌看板正常展示；车型看板标明缺项，最终数量显示“未计算” |
| 销售数据较旧 | 显示截止日、数据年龄及采用口径；演示可继续，正式运行按已有时效规则处理 |
| 一项工具查询失败 | 保留已完成结果，显示失败模块和重试入口 |
| 参数或资源冲突 | 指出冲突规则、范围及数量；保留候选供修订，不标“校验通过” |
| 运行取消或超时 | 保存已完成节点状态，不形成完整最终结果 |
| 两端同时编辑同一草稿 | 检测基础版本变化，展示差异，禁止静默覆盖 |
| 只有部分车型完成 | 展示覆盖范围；受共享运力或搭配影响的集合未校验前，不能声称全国结果可发布 |

## 6 建设顺序与验收

| 阶段 | 交付内容 | 完成判据 |
| --- | --- | --- |
| 第一阶段 | CUI建任务、分析skill、品牌/区域/路线看板 | 用现有CSV完成真实查询与汇总；两端数值和数据性质一致 |
| 第二阶段 | 情景和参数草稿、演示车型输入扩展、原引擎试算 | 同数据版本下可比较参数影响；缺输入不伪造结果 |
| 第三阶段 | 经营主体/门店解释、费用估算、版本选择及发布衔接 | 满足率可复算，费用与路线合计相符，发布沿用原校验 |

验收至少覆盖：

1. CUI 新建包含多个车型的任务，GUI 只生成一个周计划并展开车型子任务。
2. 分析期间可看到进度和已完成看板；摘要里的每个数字可打开相同版本的证据。
3. 8/9月缺失显示为空；当前品牌数据不会伪装成逐车型明细。
4. 输入仅吉达情景后，供应降幅与道路容量分别变更，门店库存保留来源事实。
5. CUI和GUI改动作用于同一草稿；旧运行、旧消息及对比基线可追溯。
6. 结果列出逐经营主体及门店的要货满足率、有效订单及时满足率、费用和未满足原因。
7. 降低目标WOS后，同步保留固定需求分母的比较，不把分母变化当作服务改善。
8. 同路线多个车型共用一次容量；库存、渠道预算、供给守恒及政策搭配符合原模块规则。
9. 正式数据不足时停留在分析或演示结果；“已发布周计划”与“已发运”状态分开。

本轮已延伸至本地前端演示：任务、分析 Dashboard、策略草稿、三方案试算、经销商覆盖与费用、历史版本和图谱联动。生产订单及时满足率、实际港口/VPC释放、B11资源优化及正式发布仍待接入。业务尚未给出的供应降幅、实际港口限制、目标权重等，作为运行时显式输入保留；具体示例和默认演示取值见第三份文档。
