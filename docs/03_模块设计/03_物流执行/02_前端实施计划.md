# 物流执行前端实施计划

> 实施方式：使用 superpowers:executing-plans 在当前会话连续实现；依照 test-driven-development 验证行为。

**目标：** 将物流页签升级为承接整次分车的 CUI＋GUI 工作台，分析、比较和执行检查共用 Skill 命令、数据与历史版本。

**架构：** 新增独立 logistics 业务模块，复用 Workspace 的 CUI 执行轨迹及 Session 持久化。全国演示生成可核对的门店×车型需求；纯函数完成资源分析和条件排程；用户在 GUI 确认模拟委托与回执。旧27台与调拨流程保留在教学入口。

**技术：** Next.js 16（本机验证版本 16.3.7）、React 19、TypeScript、本地 IndexedDB、node:test、Playwright。遵循本地 Next.js use-client 指南，无新增运行依赖。

**设计依据：** [物流执行故事线](./01_物流执行故事线与成本优化方案.md)。

## 全局约束

- 全国演示固定2,010台供给背景、1,800台分车、210台未分配，79店、18城、15车型；所有新增明细明确标为模拟。
- 全量城市数量必须对回文档；SC-WEST路线缺口36台，城市理想233趟道路费819,287 SAR只作为粗估。
- 24台仅是局部解释，不放大全国节省；旧27台任务不与全国量混加。
- 方案基于有效交期、释放时间及资源；缺承运或车辆信息不能表示真实可执行。条件排程与模拟确认分开。
- CUI与GUI都经过同一个业务命令入口；原分析/比较版本不可覆盖；过滤不缩小全网占用。
- 已发布分车可导入；未发布候选不冒充已发布计划；重复导入不重复增加需求。
- 保存、恢复和重置遵循当前 Session 隔离；原业务回归保持可用。

## 重点复核

1. 模型、城市、门店和释放分组数量守恒，品牌资格与局部子集不重复。
2. 修改参数后旧比较不能确认，历史消息必须打开其原版本。
3. 有活动分车任务时，物流请求不得误入分车解析；未知或无效参数不静默应用。
4. 同一批次不能重复发运、超量/逆向签收；取消只允许未发运批次；全国汇总按根需求核销。
5. 旧浏览器快照缺 logistics 字段时可迁移，新Session及重置不能继承其他Session物流数据。
